# 운영 런북

공통 제작·병렬 검토·발행 종료 절차는 [NEWS 제작과 발행](../../docs/news-production.md)을 함께 적용한다. 절차 문서는 글별 현재 상태를 대신하지 않는다. 역할 세션의 파일·해시가 실제 공개 대상 원고와 다르면 새 인계를 접수하며, 기존 결과는 이력으로 보존한다.

## 콘텐츠 흐름

1. `편집대기열`에서 콘텐츠 ID를 선택한다.
2. 실제 검색어와 독자 질문을 연결한다.
3. 공식 출처와 재사용할 연구 노트를 지정한다.
4. 문제·수식·선행 방법·새 방법·실험·한계를 연구 온톨로지로 정리한다.
5. 핵심 수식의 기호·단위·가정·경계조건과 이번 연구에서 달라진 항을 검토한다.
6. GitBlog 원천 글과 내부 링크를 작성한다.
7. 물리적 배경, 방법 비교, 수식 지도, 결과·한계 중 3~5개의 시각자료를 만든다.
8. `미디어저작권`에서 모든 자산의 권리 상태를 확인한다.
9. Blogger HTML과 Instagram 배포 패키지를 생성한다.
10. 사람 승인을 받은 뒤 채널별 발행을 실행한다.
11. 공개 URL과 미디어·링크를 확인한다.
12. `실행로그`와 검색·소셜 성과를 갱신한다.

## 채널별 깊이 분리

같은 연구를 모든 채널에 같은 문장과 분량으로 복사하지 않는다.

- GitBlog는 공학 원문이다. `L0 → L1 → L2 → L3`를 모두 포함하고, 핵심 수식·선행 방법·실험 조건·실패 조건까지 검토한다.
- Blogger는 주제를 처음 검색한 독자를 위한 쉬운 진입 글이다. 1,500~2,500자를 기준으로 `L0 → L1 → L2-light`까지만 다루되, 단순 홍보 요약으로 줄이지 않는다.
- Blogger의 기본 흐름은 `한 문장 답 → 일상적 비유 → 필요한 기초 개념 → 무엇이 달라졌나 → 핵심 그림 또는 수식의 말뜻 → 가장 큰 한계 → 더 깊은 GitBlog 해설`이다.
- Blogger에는 역할이 분명한 이미지나 도식 2~3개를 둔다. 원문 Figure를 사용하려면 GitBlog와 동일한 권리 검사를 통과해야 한다.
- Blogger 제목은 실제 검색 질문을 자연스럽게 반영하고, 본문은 GitBlog 문장을 그대로 복사하지 않는다.
- GitBlog 공개 URL이 아직 없거나 실페이지 검증에 실패했다면 Blogger의 `더 깊게 보기` 링크를 확정하거나 공개 발행하지 않는다.
- 어느 채널이든 같은 콘텐츠 ID를 사용하되 원고 버전과 승인 범위는 채널별로 기록한다.

기존 공개 글의 Blogger 파생본은 자동 소급 발행하지 않는다. 검색 의도, 중복 여부, 최신성, 미디어 권리를 다시 검사하고 콘텐츠별 승인을 받은 글만 순서대로 전환한다.

## 공대 독자 깊이 게이트

긴 글이라는 이유만으로 깊이 검사를 통과시키지 않는다. 아래 네 층이 서로 연결돼야 한다.

1. `L0`: 30초 안에 읽는 결론, 증거 등급, 아직 모르는 것
2. `L1`: 현상과 직관, 공학 시스템에서 이 문제가 등장하는 위치
3. `L2`: 핵심 수식, 기호와 단위, 가정과 경계조건, 간단한 수치 예제
4. `L3`: 선행 방법의 계보, 이번 방법이 바꾼 항 또는 제약, 실험적 결과, 실패 조건과 미해결 문제

수식은 장식으로 넣지 않는다. 각 수식에는 다음을 기록한다.

- 종류: 지배 방정식, 목적함수, 추정식, 갱신식, 제약식, 평가 지표 중 하나
- 원문 위치: 섹션·페이지·식 번호
- 기호·단위·차원과 필요한 선수 개념
- 성립 가정과 경계조건
- 기존 방법이 다룬 방식과 한계
- 이번 연구가 새로 푼 부분과 여전히 풀지 못한 부분
- 수학적 변화가 실제 실험 지표에 미친 영향

핵심 방법이나 수식의 원문 위치를 확인할 수 없으면 `NOT_ENOUGH_DEPTH`로 보류한다. 논문이 수식을 사용하지 않는 산업 발표라면 공정 흐름, 물리량, 비교 기준과 시스템 경계를 같은 수준으로 검토한다.

## 지식 그래프와 토큰 절약

Google Sheets는 승인과 운영 상태를 관리하는 control plane으로 유지한다. 연구 지식의 원본은 로컬 SQLite에 정규화하고, 공개 사이트에는 독자가 볼 수 있는 관계만 JSON으로 투영한다. 클라우드 그래프 DB는 원본이 아니라 선택적 시각화 미러다.

토큰을 줄이기 위해 다음 순서로 실행한다.

1. 후보 단계에서는 제목·초록·메타데이터만 읽는다.
2. Top 3만 관련 연구와 증거 위치를 비교한다.
3. Top 1만 본문·보충자료·코드에서 핵심 구간을 추출한다.
4. 문서 해시와 추출 구간을 캐시하고, 다음 실행에서는 변경된 부분만 처리한다.
5. 글을 쓸 때 전체 PDF 대신 관련 수식·방법·결과 노드의 1~2 hop만 가져온다.
6. 분류·중복 제거·JSON 정규화는 저비용 모델이나 결정적 코드가 맡고, 고비용 모델은 수식 검토와 최종 서술에만 사용한다.
7. 모델의 긴 사고 과정은 저장하지 않고 출처 위치, 주장, 관계, 실패 사유만 보존한다.

## 자동화 범위

자동 실행해도 되는 일:

- 콘텐츠 목록, 제목, 소제목, 내부·외부 링크 추출
- 실제 검색어 수집과 의도 초벌 분류
- 출처·미디어 원장 누락 검사
- 연구 패키지의 온톨로지 추출과 기존 방법 연결
- 수식 기호·단위·원문 위치 누락 검사
- Blogger HTML, Instagram 캡션·카드 문안·영상 스토리보드 생성
- 링크 상태, 이미지 경로, 대체 텍스트, 비율 검사
- 공개 페이지 확인과 Google Sheets 실행 로그 갱신

사람 승인이 필요한 일:

- GitBlog 원고의 최종 주장과 제목
- 권리 해석이 필요한 타인 저작물 사용
- Git push, Blogger 공개 발행, Instagram 공개 게시
- 협찬·제휴·광고 표시 여부

## Instagram 연결 전 상태

현재 Instagram 채널은 `export-only`다. 하네스는 카드 문안, 캡션, 해시태그, 원문 링크, 4:5·9:16 제작 지시서까지 만든다. 자동 게시를 켜려면 Meta가 지원하는 계정 유형과 게시 API 권한을 별도로 연결하고, 테스트 계정에서 게시·삭제·오류 복구를 검증해야 한다.

## 저작권 재점검

- 새 자산: 발행 전마다 검사
- 라이선스 URL 또는 외부 제공 자산: 매월 검사
- 기간 제한 허가·음원: 만료 30일 전 알림
- 권리 불명, 삭제된 원본, 조건 변경: 관련 채널의 재발행을 즉시 차단


## 독자용 최종본의 편집 정보 정리

매 제작·수정 묶음에서 발행 전 한 번 수행한다. 후보 순위·점수·선정 상태 코드·내부 contentId·정규화 제목·점수 산식과 ‘후보 기록’은 비공개 인계 원장에 보존하고 독자 본문에서는 제거한다. 토글 안에 옮겨 숨기는 방식으로 내부 기록을 게시하지 않는다. 원문 제목·DOI·공식 URL은 하단 출처에 보존한다. 원문 열람 범위는 하단의 기본 접힘 ‘원문 확인 범위’에 간결하게 둔다. 동물/임상 단계·핵심 불확실성·주장 해석을 바꾸는 한계는 본문에 남긴다. 정리 작업은 검토 완료나 발행 승인으로 취급하지 않는다.

선택한 최종 원고는 `node scripts/news-reader-copy-check.mjs <원고 절대 경로>`로 검사한다. 기본 명령 `pnpm news:reader-copy-check`는 현재 10월 20일 묶음 3편과 2026-10-26 이후 공개 NEWS 원고를 검사한다. 과거 글 전체를 자동 변경하지 않으며 새 비공개 후보 기록의 보관은 허용한다. 구조 검사는 내부 정보 누출만 탐지하므로 사실·수식·그림·권리·실제 화면 검수는 별도로 유지한다.


## 분량보다 내용의 밀도와 연결

2026-10-26 사용자 기준: GitBlog 본문은 10,000자를 넘어도 된다. 분량의 상한·하한을 통과 기준으로 쓰지 않는다. 각 절은 질문에 답하거나 필요한 선수 개념·원문 근거·수식의 해석·비교 조건·한계 중 하나를 더해야 한다. 같은 주의문 반복과 분량 채우기는 줄인다. 실제 본문 글자 수와 산정 방식, 원문→본문 핵심 누락, 시각자료별 역할을 따로 기록한다. 그림 세 장을 채웠다는 이유만으로 원리·방법·결과 설명이 완성됐다고 판정하지 않는다.


## 중복 검수를 줄이는 시트 재개 규칙

작업 시작 때 Google Sheets 편집대기열의 해당 콘텐츠 ID 행을 실제로 읽고, 단계·의존성/차단·완료 조건·다음 행동 및 메모의 원고 해시를 확인한다. 로컬 상세 원장은 근거 저장소이며 시트의 현재 진행 상태를 대신하지 않는다. ID가 없으면 중복을 확인한 뒤 승인된 범위에서 기존 열·유효성 규칙을 보존해 추가한다.

검수가 끝나거나 보류 사유가 확정되면 같은 행의 완료한 범위와 남은 항목·재개 조건을 갱신하고 실행로그에 실제 수행 결과를 남긴다. 완료 조건 셀에는 완료 범위와 남은 발행 조건을 구분한다. 원고 해시·자산·설정이 유지되면 검증 근거를 읽어 재사용하고, 변경된 범위만 재검사한다. 이전 PASS를 해시만 바꿔 재사용하지 않는다. 커넥터 쓰기 후 실제 셀 값을 재조회해야 동기화 완료다. 실패하면 로컬에 PENDING으로 보존하고 시트 저장 성공이라고 말하지 않는다. 새 상태 열·탭·유효성 규칙은 별도 승인 없이 만들지 않는다.
