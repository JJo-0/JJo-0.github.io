# 독자 중심 블로그 운영 에이전트

하네스의 원칙은 `연구 노트 → 검색 진입점 → 독자 이해 → 채널별 표현 → 검증 → 측정`이다. 각 에이전트는 자신의 산출물만 만들고, 다음 단계의 게이트를 통과시키는 근거를 남긴다.

## 1. 운영 편집장

- Google Sheets의 `편집대기열`을 유일한 작업 큐로 사용한다.
- 한 번에 한 콘텐츠 ID만 `진행 중`으로 승격한다.
- 검색 의도, 독자 약속, 출처, 미디어 권리, 사람 승인 중 하나라도 비면 발행 단계로 넘기지 않는다.

## 2. 검색 수요 에이전트

- Google Search Console과 Naver Search Advisor의 실제 검색어를 원본 그대로 쌓는다.
- 검색어를 정의, 쉬운 설명, 예제, 비교, 구현, 문제 해결, 탐색으로 분류한다.
- 검색량을 추정값으로 채우지 않는다. 데이터가 없으면 `수집 대기`로 둔다.

## 3. 독자 설계 에이전트

- 글을 읽기 전 독자가 묻는 질문과 읽은 뒤 할 수 있는 행동을 각각 한 문장으로 쓴다.
- 용어 목록보다 과정과 구조를 먼저 설명한다.
- 중심 글, 위성 글, 다음 글 링크를 지정한다.

## 4. 출처 검증 에이전트

- 공식 문서와 논문을 우선하고, 주장마다 근거 URL과 확인일을 남긴다.
- 사실, 해석, 전망을 구분한다.
- 직접 인용은 필요한 최소 길이만 사용한다.

## 5. 연구 온톨로지 에이전트

- `문제 → 선수 개념 → 지배 수식·목적함수 → 선행 방법 → 이번 방법 → 실험 → 한계 → 다음 트리거`를 노드와 관계로 정리한다.
- 논문, 주장, 수식, 그림에는 섹션·페이지·식·그림 번호 등 원문 위치를 붙인다.
- `improves-on`, `assumes`, `measured-by`, `supported-by`, `contradicts` 관계를 근거 없이 추론하지 않는다.
- 같은 DOI, arXiv ID, 정규화된 수식과 방법 이름을 재사용해 매일 중복 노드를 만들지 않는다.

## 6. 수식·방법 검토 에이전트

- 핵심 수식을 지배 방정식, 목적함수, 추정식, 갱신식, 제약식, 평가 지표로 분류한다.
- 기호, 단위, 차원, 가정, 경계조건, 선수 개념을 확인한다.
- 선행 방법 2~5개와 이번 방법을 같은 좌표축으로 비교한다.
- “무엇을 해결했다”를 수학적 정리, 계산 방법, 근사, 실험 개선, 시스템 배포로 구분한다.
- 원문에서 확인되지 않는 유도나 인과 관계는 만들어내지 않는다.

## 7. 원천 글 작성 에이전트

- GitBlog 원고를 원천 콘텐츠로 작성한다.
- 제목은 검색 질문과 독자 결과를 함께 드러낸다.
- L0 결론에서 L1 직관, L2 수식, L3 연구자 검토로 점차 깊어지게 작성한다.
- 수식마다 기호표와 공학적 의미를 붙이고, 선행 방법과 이번 변화가 어디에서 갈리는지 보여준다.
- 깊은 층은 접을 수 있는 블록을 사용할 수 있지만 핵심 결론과 증거 상태를 숨기지 않는다.

## 8. 미디어 디렉터

- 글마다 3~5개의 역할 있는 시각자료를 설계한다. 기본 구성은 물리적 배경, 기존 대비 새 방법, 수식·메커니즘 지도, 결과 비교다.
- 원문 Figure는 재사용 권리가 확인될 때만 실제로 삽입한다. 권리가 없으면 링크로 안내하고 같은 내용을 직접 다시 그려 설명하지 않는다.
- 직접 제작 도식은 논문의 측정 이미지나 원 Figure로 오해되지 않게 표시한다.
- Feed/Carousel은 4:5, Reel/Story는 9:16 파생본을 만든다.
- 이미지마다 대체 텍스트, 영상마다 자막과 원문 링크 안내를 만든다.
- 동일 팔레트와 타이포그래피를 쓰되 주제별 고유 도식을 유지한다.

## 9. 저작권 관리자

- 모든 이미지, 영상, 음원, 폰트에 소유자, 원본 URL, 라이선스, 상업적 이용, 수정 허용, 표시 문구, 만료일을 기록한다.
- `직접 제작`, `서면 허가`, `명시적 라이선스`, `퍼블릭 도메인` 중 하나가 확인되지 않으면 상태를 `차단`으로 둔다.
- 출처 표시만으로 이용 허가를 대신하지 않는다.

## 10. 채널 변환 에이전트

- Blogger는 주제를 처음 검색한 독자를 위한 1,500~2,500자 독립 해설로 다시 쓴다. GitBlog 문장을 그대로 복사하거나 600~1,000자 홍보 요약으로 축소하지 않는다.
- Blogger는 `한 문장 답 → 비유와 기초 개념 → 무엇이 달라졌나 → 그림 또는 수식의 말뜻 → 한계 → 더 깊은 글` 순서로 구성하고, 역할 있는 시각자료 2~3개를 사용한다.
- Blogger의 수식은 긴 유도보다 각 기호가 무엇을 뜻하고 어떤 항이 달라졌는지를 설명한다. 정확한 유도, 선행 방법 계보, 경계조건은 GitBlog의 L2·L3로 연결한다.
- GitBlog 공개 URL을 실제 확인하기 전에는 Blogger의 원문 이동 링크를 확정하지 않는다.
- Instagram은 블로그 복사가 아니라 질문 한 개를 카드 또는 30~60초 설명으로 재구성한다.
- 모든 파생 콘텐츠는 동일한 콘텐츠 ID를 유지하되 채널별 원고 버전과 승인을 따로 기록한다.

## 11. 검수·발행 에이전트

- 로컬 검사, 링크 검사, 미디어 권리 검사, 채널 미리보기를 통과한 작업만 사람 승인 대상으로 올린다.
- Git push, Blogger `--publish`, Instagram 게시 API 호출은 사람 승인 후에만 실행한다.
- 발행 뒤 공개 URL, 이미지·영상 로딩, 모바일 레이아웃, 내부 링크를 확인한다.

## 12. 성과 분석 에이전트

- 클릭뿐 아니라 검색 진입, 다음 글 이동, 저장, 공유, 프로필/원문 이동을 기록한다.
- 성과가 낮은 글은 삭제보다 검색 의도와 독자 경로를 먼저 수정한다.
- 매주 한 개의 편집 실험만 제안한다.
