## 1. 한 문장 결론: 정답 코드 하나보다 역할을 나눈 알고리즘 묶음

LACE는 대규모 언어모델(LLM)에게 최적화 코드 하나를 곧바로 완성하라고 요구하지 않는다. **입출력·검증 도구를 먼저 연결하고, 서로 다른 사례에서 강한 휴리스틱 여러 개를 진화시켜 묶음으로 남긴다.** 2026년 10월 1일 Nature Machine Intelligence에 발표된 연구는 기존 36개 조합최적화 문제에서 평균 벤치마크 점수 0.945를 보고했다. 이는 성공 확률이나 실제 물류비 절감률이 아니다.<Cite n={1} />

이 글은 10월 2일 편집안에 따라 선정했으며, 실제 게시와 자료 확인은 10월 5일에 진행했다. 논문 초록, 공개 보충자료와 공식 구현을 대조했다. 첨부안의 99점은 편집상 평가이지 학술지의 공식 점수나 수상 기록이 아니다. 중요한 변화는 ‘모든 전문가를 대체한 AI’라는 선언보다 **검증 가능한 경계 안에서 알고리즘을 탐색하는 공정**이 구체화됐다는 데 있다.

### 이 그래프 읽기: 0.945를 백분율로 바꾸지 않는다

막대는 논문 초록에 보고된 36개 문제의 평균 점수 0.571, 0.870, 0.945를 다시 그린 것이다. 논문 원도판을 복제한 그림도, 새 실험을 수행한 결과도 아니다. 같은 평가 아래 LACE의 점수가 높았다는 비교만 보여준다. 최적해를 찾은 횟수, 계산 시간, 실패율은 각각 별도의 지표다. 막대 끝을 94.5%라고 읽어 모든 문제의 최적성이나 신뢰성을 보증해서는 안 된다.<Cite n={1} />

## 2. 왜 이 문제가 어려운가: 제약을 만족하는 것부터 시작한다

배송 순서, 공장 작업 순서, 컨테이너 배치처럼 선택을 조합하는 문제에서는 가능한 경우가 빠르게 늘어난다. 무엇을 가장 작게 또는 크게 만들지 정한 것이 <strong>목적함수(objective)</strong>이고, 반드시 지켜야 하는 조건이 <strong>제약조건(constraint)</strong>이다. 좋은 점수라도 제약을 어겼으면 사용 가능한 해가 아니다. LLM이 보기 좋은 Python을 작성했는지와 실제 일정이 가능한지는 서로 다른 검사다.

새 제약이 추가되면 알고리즘만 수정하는 것으로 끝나지 않는다. 입력 파일을 어떻게 읽는지, 출력에 어떤 결정이 들어가야 하는지, 실패를 무엇으로 판정하는지, 시간 초과 때 무엇을 반환하는지까지 맞물린다. 이 결합을 분리하지 않으면 탐색 아이디어의 좋고 나쁨을 평가하기 전에 파싱과 형식 오류에 시간을 쓴다. LACE는 이런 구현 경계와 휴리스틱 설계를 나눈다.<Cite n={2} /><Cite n={3} />

<BeginnerGuide title="휴리스틱과 문제 instance를 처음 듣는다면">

문제는 규칙이고 <strong>instance(사례)</strong>는 그 규칙에 넣은 구체적인 데이터다. ‘정해진 기계에 작업을 배정한다’가 문제라면, 오늘의 작업 시간과 납기 목록이 하나의 사례다. 작업이 짧은 순서대로 배정하는 규칙과 납기가 빠른 순서대로 배정하는 규칙은 서로 다른 **휴리스틱**이다. 빠르게 괜찮은 답을 찾기 위한 규칙이지 모든 사례에서 최적임이 보장된 공식은 아니다.

두 규칙 가운데 어제 잘한 규칙이 오늘도 잘한다고 단정할 수 없다. 짧은 작업이 많을 때와 긴급 납기가 몰릴 때의 구조가 다르기 때문이다. <strong>포트폴리오(portfolio)</strong>는 같은 문제를 풀 수 있는 여러 알고리즘을 보관하는 묶음이다. 여기서는 금융 자산이 아니라 실행 가능한 코드의 모음이다. 서로 비슷한 코드 열 개와 서로의 약점을 보완하는 코드 열 개는 가치가 다르다.

예를 들어 두 작업이 같은 기계를 같은 시각에 사용한다면 `is_feasible()`은 거짓을 반환해야 한다. 사용 가능한 일정이라면 `objective()`가 지연 비용 등을 계산한다. 이 예시는 개념 설명이며 논문의 특정 항만 사례를 재현한 것은 아니다. 검사기가 잘못 구현되면 좋은 점수도 잘못된 규칙에 대한 좋은 점수일 뿐이다.

</BeginnerGuide>

## 3. 기존 방식과 다른 점: 생성과 평가를 한 덩어리로 두지 않는다

직접 프롬프트로 코드를 만드는 방식은 입출력 처리, 제약 검사, 탐색 전략과 예외 처리를 한 번에 해결해야 한다. 단일 휴리스틱을 반복 개선하는 방식은 평균 성능이 좋아져도 서로 다른 사례에 필요한 전문 전략을 잃을 수 있다. LACE는 문제를 **I–O–T–H**, 즉 입력 스키마, 출력 스키마, 도구 라이브러리, 휴리스틱 묶음으로 나눈다.<Cite n={1} /><Cite n={2} />

여기서 계약(contract)은 자연어 약속이 아니라 코드가 서로 연결되는 인터페이스다. I가 공급하는 필드와 O가 요구하는 필드, T가 계산하는 실행 가능성과 목적값을 H가 실제로 사용할 수 있어야 한다. 보충자료는 임시 명세를 만들고 실제 해법을 통해 끝까지 실행해 보는 검사, 별도 검토 에이전트, 제한된 수정 과정을 설명한다. 이는 계약의 연결 가능성을 확인하는 절차이며 모든 입력에 대한 형식적 정확성 증명과 같지는 않다.<Cite n={3} />

**원안에 덧붙인 중요한 확인 사항**도 있다. 보충자료 4.4절에 따르면 기존 36개 CO-Bench 문제에서는 입력 파서와 최종 채점기를 재사용한다. 출력 표현, 도구와 휴리스틱을 생성하는 부분과 구분해야 한다. 신규 문제에서 입력 생성 경로를 사용했다고 해서 기존 벤치마크의 모든 파서·평가기를 처음부터 자율 발명했다고 표현하면 부정확하다. 공식 구현도 알려진 파서를 그대로 채택하는 옵션을 제공한다.<Cite n={2} /><Cite n={3} />

## 4. 새 방법의 세 단계: 계약, 진화, 상보적 선택

첫 단계는 문제 설명과 사례 파일을 실행 가능한 인터페이스로 정리하는 것이다. 입력·출력·도구를 담당하는 역할을 분리하고, 초기 휴리스틱이 이 경로를 통과할 수 있는지 확인한다. 문제를 여러 번 풀기 전에 검사 기준을 정리하면 실패한 코드가 왜 실패했는지와 알고리즘 품질이 낮은 이유를 더 잘 구분할 수 있다. 단, 자연어 제약을 잘못 이해한 오류까지 자동으로 사라지는 것은 아니다.<Cite n={3} />

두 번째 단계에서는 여러 후보를 진화시킨다. 공식 자료는 LR, RR, CC, CS, DI라는 다섯 생성 연산과 ER, EI라는 두 수정 연산을 제공한다. 기존 코드의 변형, 반성적 재설계, 상보적 교차, 비교·종합, 다양성 주입으로 후보를 만들고 실행 오류와 시간 초과를 수정한다. **좋은 해를 찾는 능력과 실행 가능한 코드를 유지하는 능력은 별도 역할**이다. 보충자료의 연산 제거 실험에서도 두 종류를 구분한다.<Cite n={2} /><Cite n={3} />

세 번째 단계는 남길 코드를 선택하는 것이다. 평균 1등을 복제하는 대신 사례별 순위를 이용하는 혼합정수선형계획(MILP)이 서로 보완하는 집합을 고른다. 원래 물류 문제 전체를 MILP로 풀었다는 뜻이 아니라 **후보 알고리즘 가운데 어떤 묶음을 유지할지**에 MILP를 사용한다. 숫자의 절대 크기가 다른 사례를 단순 합산하는 대신 순위로 비교한다는 점도 중요하다.<Cite n={3} />

### 교육용 그래프 읽기: 평균 1등과 최고의 묶음은 다르다

위 네 사례의 비용은 이 글에서 만든 가상 값이다. 전문가 1은 A·B에서 8, C·D에서 20이고 전문가 2는 반대다. 일반 전략은 항상 11이다. 하나만 고르면 평균 비용 11인 일반 전략이, 평균 14인 두 전문가 각각보다 좋다. 그러나 두 전문가를 실행하고 사례마다 좋은 결과를 남길 수 있다면 평균은 8이다. 이 예시는 상보성을 설명할 뿐 LACE의 실제 수치나 특정 선택 정책의 성능을 재현하지 않는다.

<CandidateEquation id="lace-portfolio-mean" title="왜 평균 1등 하나보다 두 전문가의 묶음이 나을 수 있나?" tex={String.raw`C(P)=\frac{1}{m}\sum_{i=1}^{m}\min_{h\in P}c_{ih}`}>

P는 보관한 알고리즘 집합, m은 사례 수, c는 각 알고리즘의 비용이며 낮을수록 좋다고 가정한다. 먼저 사례별로 집합 안의 최소 비용을 고른 다음 평균을 구한다. 위 예시에서는 두 전문가의 최소값이 모두 8이므로 C(P)=8이다. 일반 전략 하나만 두면 C(P)=11이다. 이 식은 **교육용 best-of-set 비용 정의**이며 논문의 순위 기반 MILP 목적식을 그대로 옮긴 것이 아니다.

핵심은 연산 순서다. ‘각 알고리즘의 평균을 구한 뒤 하나를 선택’하는 것과 ‘사례별 최선을 고른 뒤 평균’하는 것은 같지 않다. 또한 최소값은 공짜로 알려지지 않는다. 여러 해법을 실행해 검사하거나 어떤 해법을 쓸지 선택해야 한다. 실제 운영 비교에는 알고리즘 수, 병렬 자원, 전체 실행 시간과 선택 비용까지 같은 경계로 넣어야 한다.

</CandidateEquation>

## 5. 핵심 실험: 평균 점수와 실행 가능성을 따로 읽는다

공개 초록은 기존 36개 문제에서 LACE 0.945, 가장 강한 기존 LLM 방법 0.870, 프레임워크 없는 직접 프롬프트 0.571을 보고한다. 신규 네 문제에서는 0.97–0.99이며 비교한 다섯 LLM 기반 방법이 실행 가능한 알고리즘을 만들지 못했다고 적는다. **이 다섯 방법은 모든 최적화 솔버를 뜻하지 않는다.** 보충자료에는 별도의 메타휴리스틱과 Gurobi 비교 설정도 설명돼 있다.<Cite n={1} /><Cite n={3} />

공식 보충 웹페이지는 Avg Score, Valid Rate, Survival Rate를 구분한다. 따라서 평균 점수만 높아도 어려운 사례의 실패가 사라졌다고 말할 수 없다. 보충자료의 선택 방식 제거 실험은 후보 생성과 데이터 분할을 유지하며 선택 규칙을 바꾸고, 평균 점수와 어려운 사례의 성과가 다르게 움직일 수 있음을 보여준다. 도구와 포트폴리오를 제거한 주논문 Figure 4는 공개 초록만으로 세부 효과 크기를 재계산하지 않았다.<Cite n={3} /><Cite n={4} />

## 6. 공개 코드가 강점이어도 재현의 층은 다르다

공식 저장소는 40개 문제의 정확한 7,109개 시험 사례 목록, 문제 계약, 최종 10개 휴리스틱과 재현 스크립트를 제공한다. 한 파일에 여러 사례가 들어갈 수 있으므로 파일 개수가 사례 수와 같지는 않다. `instances.json`과 검증 스크립트로 사례 집합을 확인하도록 안내한다. 코드·자료 공개와 고정된 Zenodo 보관본은 결과를 추적할 수 있게 한다.<Cite n={2} /><Cite n={5} />

**배포된 포트폴리오를 평가하는 일**과 **처음부터 새로운 포트폴리오를 진화시키는 일**은 다르다. 전자는 이미 작성된 알고리즘을 실행하는 경로로 API 키가 필요하지 않지만, 후자는 외부 LLM API, 선택한 모델과 샘플링에 의존한다. 같은 저장소를 받았다는 사실만으로 API의 미래 응답까지 고정되는 것은 아니다. 재현에는 데이터·코드 버전뿐 아니라 모델 식별자, 실행 조건과 자원 사용을 기록해야 한다.<Cite n={2} />

이번 게시 작업은 논문의 새 알고리즘 생성 실험을 실행하지 않았다. Colab이 제공된다는 사실을 ‘Colab에서 전 실험 재현 성공’으로 바꾸지도 않는다. 외부 생성 코드를 실제 업무 시스템에서 실행하려면 별도 격리와 자원 제한, 파일·네트워크 접근 제한이 필요하다. 실행 검사를 통과했다는 연구 설명은 운영 보안 감사를 대신하지 않는다.

## 7. 한계와 반대 증거: 무엇이 자동화 밖에 남나

신규 문제 네 개는 모두 항만 스케줄링·예인선 경로 계열이다. 구조적으로 새로운 제약을 조합했다는 시험은 의미가 있지만, 의료·전력망·로봇의 모든 문제로 영점 조정 없이 일반화했다는 증거는 아니다. 또한 분명한 목적함수와 실행 가능성 검사를 쓸 수 있다는 전제가 있다. 현실의 정책 문서가 충돌하거나 작업자의 예외 판단이 암묵적이면 그 검사기를 올바르게 만드는 일 자체가 어렵다.<Cite n={1} /><Cite n={3} />

스모크 테스트는 적어도 한 경로가 연결돼 실행된다는 증거다. 극단값·누락값·새 제약에도 항상 맞는다는 증명은 아니다. 특히 생성된 도구가 누락한 제약을 생성된 휴리스틱도 똑같이 무시하면 내부 검사만으로 결함을 놓칠 수 있다. 이 문장은 논문에서 그런 사고가 관측됐다는 주장이 아니라, 생성기와 검사기를 함께 사용하는 설계에서 따로 확인해야 하는 위험에 대한 설명이다.

시간 예산도 해석 경계를 정한다. 해법을 설계하는 데 쓴 API 비용, 개발 사례 평가 비용, 마지막 포트폴리오 실행 비용을 구분해야 한다. 높은 평균 점수가 실제 공장의 총비용 우위를 뜻하지는 않는다. 논문은 특정 문제·비교법·조건의 결과이며, 모든 하드웨어와 시간 예산에서 상용 MILP·CP 솔버를 이겼다는 보편 명제가 아니다. 저자들은 경쟁적 이해관계가 없다고 공개했다.<Cite n={1} /><Cite n={2} /><Cite n={3} />

## 8. 실제로 달라질 수 있는 것과 다음 확인점

이 연구가 제시한 실용적 방향은 ‘문제 규칙을 고정하고 AI가 후보를 탐색하게 한 뒤 실행 결과로 고른다’는 반복 구조다. 사람은 좋은 코드 한 편을 직접 작성하는 역할뿐 아니라 문제 계약, 평가 분할, 실패 조건과 계산 예산을 검토하는 역할을 맡는다. 단순한 에이전트 수보다 **무엇을 평가기로 인정하고 무엇을 보존할지**가 설계의 핵심이 된다.

다음에는 항만 밖의 새로운 문제, 동일한 총 실행 시간·계산비의 비교, 여러 독립 반복 실행과 실패 분포를 봐야 한다. 실제 운영 자료의 노이즈와 제약 변경에 대응할 때 오래된 포트폴리오를 언제 폐기하고 다시 검증할지도 중요하다. 더 높은 평균 하나보다 재현 가능한 실패 경계가 운영 의사결정에 더 유용할 수 있다.

결론은 첨부안의 취지를 유지한다. **검증 가능한 계약 안에서 서로 보완하는 알고리즘을 자동 진화시키는 방식이 강력한 수준에 도달했다.** 다만 계약의 의미를 정확히 정하는 책임, 평균과 최악 사례를 나누는 평가, 생성 비용과 운영 비용을 합친 비교까지 자동으로 끝난 것은 아니다. 이 구분을 유지해야 연구용 알고리즘 발견과 실제 알고리즘 엔지니어링 자동화를 혼동하지 않는다.
