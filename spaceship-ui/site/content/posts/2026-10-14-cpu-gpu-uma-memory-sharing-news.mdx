## 이 글에서 알아갈 것

CPU와 GPU가 같은 물리 메모리를 사용해도, 한쪽이 쓴 최신 값이 다른 쪽에 자동으로 보이는 것은 아니다. 이 글은 먼저 **주소를 공유하는 일**, **데이터가 보이는 일**, **동시에 갱신할 때 값이 보존되는 일**을 구분한다. 다음으로 연구가 네 플랫폼에서 수행한 단일 송신자·수신자 정확성 검사와 데이터 전달·동기화 성능 비교를 살펴본다. 마지막에는 응용마다 다른 기준 시간과 Figure 14의 “요청 시간 추정”이 무엇을 뜻하는지 확인한다.

**UMA**(Unified Memory Architecture)는 CPU와 GPU가 한 물리 메모리 체계를 함께 쓰는 구조를 말한다. <strong>일관성(coherence)</strong>은 한 처리장치의 변경이 다른 처리장치의 읽기 경로에 어떻게 반영되는지에 관한 규칙이다. 두 말은 같은 뜻이 아니다. 공용 창고를 쓴다고 해서 작업자가 각자 들고 있는 목록이 즉시 새로 고쳐지는 것은 아니라는 비유로 시작할 수 있지만, 이 비유는 실제 캐시 프로토콜을 재현하지 않는다.

## 먼저 그림으로: 주소를 같이 쓰는 것과 데이터를 복사하는 것

<NewsFigure media="uma-v1-figure2" />

그림 왼쪽은 CPU와 GPU가 각각 자기 메모리를 쓰는 구성을, 가운데는 UMA를, 오른쪽은 링이나 NoC 같은 연결과 추가 하드웨어 구성의 차이를 보여 준다. 여기서 중요한 것은 그림 속 선이 실제 칩의 배선을 축척대로 그렸다는 뜻이 아니라는 점이다. 캡션은 논리적 연결을 나타낸다고 설명한다. 예를 들어 링의 공유 LLC도 한 덩어리로만 놓인 것이 아니라 코어 주변에 물리적으로 나뉘어 있을 수 있다. 이 그림은 “UMA면 항상 같은 방식으로 빠르다”는 결론을 주지 않고, 플랫폼마다 내부 구조가 다를 수 있음을 보여 준다. ([원문 §2.1 및 Figure 2](https://arxiv.org/html/2610.13125v1#S2.F2.fig1))

<NewsFigure media="uma-v1-figure3" />

왼쪽의 데이터 복사는 한쪽 메모리의 값을 다른 쪽 메모리로 옮기는 단계와 그에 따른 저장 공간을 요구한다. 오른쪽의 직접 접근은 양쪽이 읽고 쓸 수 있는 동일 영역을 이용해 복사 단계를 줄일 수 있다. 하지만 직접 접근도 공짜는 아니다. 하드웨어가 양쪽에 접근을 허용해야 하고, 읽기·쓰기 순서와 캐시 처리가 맞아야 한다. 그러므로 “복사 없는 경로”는 “비용 없는 경로”나 “항상 더 빠른 경로”와 같지 않다. ([원문 §2.3 및 Figure 3](https://arxiv.org/html/2610.13125v1#S2.SS3))

## 최신 값이 보이는 것과 동시에 바꾸는 것은 다르다

CPU가 캐시에 새 값을 썼다고 해 보자. GPU가 읽는 경로가 아직 그 변경을 보지 못하면 GPU는 이전 값을 읽을 수 있다. 반대로 GPU가 쓴 값을 CPU 쪽의 오래된 캐시가 가릴 수도 있다. 그래서 “같은 주소에 접근할 수 있다”와 “정해진 시점에 상대가 최신 값을 읽는다”는 별도 조건이다.

논문은 메모리 공유를 **Bind, Write, Read, Unbind** 작업으로 나눠 정확성을 시험한다. Bind는 공유 영역과 접근 속성을 준비하는 단계, Write는 데이터를 기록하는 단계, Read는 상대가 값을 가져오는 단계, Unbind는 연결을 끝내는 단계다. 같은 호출 이름을 썼다고 모든 플랫폼에서 같은 하드웨어 동작을 보장하는 것은 아니다. 페이지 크기, CPU/GPU 캐시 정책, 일관성 방식, 읽기·쓰기 경계에 따라 지원 가능한 조합이 달라진다. ([원문 §4.1, Table 1, Figure 4](https://arxiv.org/html/2610.13125v1#S4))

### 연구의 정확성 검사는 무엇을 확인했나

§4.1의 기본 검사는 송신자 한 명이 정해진 패턴을 쓰고 수신자 한 명이 읽은 뒤, 받은 각 단어가 기대한 값과 일치하는지 확인한다. 저자들은 단일 수신 GPU 커널을 지속 실행하는 방식으로 읽기 결과를 검사하고, 장치 오류나 시간 초과는 데이터 불일치와 구별한다. 이 절차는 시험한 플랫폼과 설정에서 CPU–GPU 간 데이터 가시성을 확인하는 **경험적 검사**다. 모든 프로그램·모든 장치·모든 타이밍에서 맞다는 수학적 증명은 아니다.

더 중요한 경계가 있다. 송신자 하나와 수신자 하나가 값을 정확히 주고받았다고 해서, 여러 처리장치가 같은 카운터를 동시에 늘려도 갱신이 보존된다는 뜻은 아니다. 동시 읽기–수정–쓰기에는 원자성(atomicity)이 필요하다. 저자들은 별도의 이산 GPU 검사에서 원자 연산 API 호출이 오류 없이 끝났는데도 CPU가 같은 카운터를 동시에 갱신하자 일부 증가가 유실된 관찰을 기록한다. 이것은 검사한 조건에 대한 사례이며, 모든 GPU·모든 메모리에서 API가 실패한다는 일반 법칙은 아니다. ([원문 §4.1.4](https://arxiv.org/html/2610.13125v1#S4.SS1.SSS4))

독자는 **가시성**과 **원자성**을 서로 다른 질문으로 두면 된다. “상대가 내가 쓴 값을 보았는가?”와 “여러 갱신이 서로 덮어쓰지 않고 모두 남았는가?”는 검증 방법도 다르다.

## 이 연구는 어떤 플랫폼과 방법을 비교했나

핵심 연구 대상은 한 방향 일관성을 지원하는 네 플랫폼이다. Raptor는 Core i5-14500/UHD 770과 링 연결, Arrow는 Core Ultra 285H/Arc 140T와 MSC가 없는 NoC, Lunar는 Core Ultra 258V/Arc 140V와 8 MB MSC, Orin은 Jetson AGX Orin의 Cortex-A78AE/NVIDIA Ampere 구성과 4 MB MSC로 설명된다. 네 시스템 모두 논문이 기술한 코어 비교에서는 one-way coherence를 사용한다. 뒤의 Appendix B에서 다루는 NVIDIA DGX Spark/GB10은 two-way coherence를 포함하는 **별도 확장**이며, 네 핵심 연구 플랫폼에 다섯 번째 장치처럼 섞지 않는다. ([원문 §§3.1–3.3, §5.2, Appendix B](https://arxiv.org/html/2610.13125v1#S3))

연구는 단순히 “공유 메모리냐 복사냐”만 비교하지 않는다. 데이터가 CPU에서 GPU로 가는지, GPU에서 CPU로 가는지, 파일 입출력 단계인지, 커널 안에서 읽고 쓰는지, 커널 사이에서 넘기는지에 따라 정책이 바뀐다. 논문과 보존된 참조자료에는 `W_A/W_F/W_B`(write-alone, write-then-flush, write-bypass)와 `R_A/R_I/R_B`(read-alone, read-after-invalidate, read-bypass) 같은 선택이 나온다. 이 표기는 연구의 옵션 이름이다. 이름만 보고 어떤 정책이 모든 장치에서 최선이라고 결론 내릴 수는 없다.

확인 가능한 비교법은 두 묶음으로 볼 수 있다.

1. **Native load-plus-copy 또는 mmap-and-copy ↔ 직접 UMA 경로.** PyTorch 모델 로딩, OpenCV 이미지 전처리, OpenVINO 출력, 점구름 전달처럼 사례마다 기준 구현이 다르다. 일부 파일 로딩 비교는 기존 복사 경로의 지연 Bind 비용을 기준에 포함한다. 따라서 같은 “복사 대 직접 접근”이라는 말 아래에서도 측정 구간과 초기화 비용이 같은지 확인해야 한다. ([원문 §§2.3, 6.1.1–6.1.2, Figures 9–10](https://arxiv.org/html/2610.13125v1#S6.SS1))
2. **기존 런타임 이벤트·CPU 위임·블록 동기화 ↔ 공유 메모리의 wait/set 또는 CAS 경로.** EdgeNN의 이벤트/직렬화 경로, GoFS의 위임 잠금, GPUfs의 블록 단위 대기 등은 서로 다른 제어 문제의 비교 기준이다. `wait/set`, 직접 잠금, grid 수준 동기화는 같은 한 숫자로 합칠 수 없다. 비교 대상이 다른 만큼 연산자 시간, 최초 토큰 지연(TTFT), 동기화 시간, 잠금 오버헤드를 각자의 분모와 함께 읽어야 한다. ([원문 §§4.1.4, 6.2.1–6.2.2, Figures 11–13](https://arxiv.org/html/2610.13125v1#S6.SS2))

### 숫자 범위를 읽는 법

초록은 네 플랫폼과 아홉 실제 응용·시스템 사례를 바탕으로 data-plane time 16–75%, control-plane overhead 7–90% 감소 범위를 보고한다. 이 범위는 사례마다 다른 구간과 비교 기준을 묶은 것이다. **모든 응용 전체가 75% 빨라졌다**는 뜻도, **모든 동기화 비용이 90% 줄었다**는 뜻도 아니다. 아홉 사례는 아홉 대의 서로 다른 물리 장치를 뜻하지 않는다.

세부 사례를 보아도 분모가 다른 이유가 드러난다. Arrow의 PyTorch 모델 로딩 사례는 복사 기준 대비 로딩 시간이 75% 감소했다고 보고하며, THP를 적용한 조건은 그 시간에서 5%를 추가로 줄였다고 설명한다. Arrow의 OpenCV 전처리 사례는 CPU 처리와 GPU 전달을 합친 해당 구간이 16% 줄었다. 별도의 OpenVINO 출력 사례는 18%의 응용 단계 감소를, 점구름 전달 사례는 복사 기준 대비 34% 감소를 보고한다. 이 숫자들은 서로 더해 새 속도 향상률을 만들 수 없다. 같은 입력, 같은 분모, 같은 구간이 아니기 때문이다. ([원문 §§6.1.1–6.1.2, Figures 9–10](https://arxiv.org/html/2610.13125v1#S6.SS1))

Control-plane 사례도 같은 원칙을 적용한다. Accelerate의 Arrow 사례는 10토큰 prefill 기준 TTFT가 11% 감소했다고 보고한다. Demand Layering의 Orin grid 방식은 블록 장벽 방식보다 해당 시간이 14% 감소하지만, 블록 수준 경로는 오히려 1.8배가 된다고 서술한다. GPUfs는 높은 블록 수 조건에서 동기화 시간이 약 7% 낮아졌고, GoFS의 Orin CPU-heavy·낮은 경합 사례는 위임 잠금 대비 잠금 오버헤드가 약 90% 낮았다. 여기서 잠금 오버헤드는 잠금 연산 한 번에 걸린 시간에서 잠금이 보호하는 임계 구역의 실행 시간을 뺀 값이다. 이 비교는 Orin에서 CPU 스레드 하나와 GPU 스레드 하나가 같은 잠금을 두고 경쟁하는 낮은 경합 조건으로, 임계 구역이 마이크로초 규모인 CPU 중심 파일 작업에서 직접 CAS 잠금과 위임 잠금을 비교했다. 여기서 11%·14%·7%·90%는 각각 다른 지표와 사례다. “전체 프로그램이 그만큼 빨라졌다”로 바꾸지 않는다. ([원문 §§6.2.1–6.2.2, Figures 11–13](https://arxiv.org/html/2610.13125v1#S6.SS2))

참조자료의 Figure 6 세로 선도 오차막대가 아니다. 보존된 참조 결과 README는 이 선을 GPU 시간에서 coherence 처리 비용이 더해지는 범위로 설명한다. `y_lower`와 `y_upper`도 신뢰구간이나 반복 측정의 분산이 아니라 그 비용 구간의 양 끝점이다. Figure 7에는 Raptor·Lunar 데이터 패널이 없고, Figure 8에는 Raptor 패널이 없다. 빈 패널은 0의 성능이나 실패한 시험이 아니다. 비교할 때는 같은 플랫폼·버퍼 크기·페이지 조건·캐시 정책·방향·동기화 방법을 먼저 맞춰야 한다. 이 참조자료의 CSV 대부분은 집계값이며 각 반복 측정의 원시 로그나 신뢰구간을 제공하지 않는다. ([고정 revision 참조 결과 안내](https://github.com/XpuOS/libumsh-artifacts/blob/880d535a86c3d82277f4c546edf386ef16ef7380/reference_results/README.md))

## Figure 14: 요청 시간을 직접 잰 것인가, 평균을 더해 추정한 것인가

<NewsFigure media="uma-v1-figure14" />

TaskBench 시나리오에서는 GLM-4.7-Flash가 작업 순서를 관리하고 ViT, SD-Turbo, DETR 세 도구를 차례로 부른다. 논문은 LLM을 `llama.cpp`, 도구를 PyTorch로 실행했다고 설명한다. 실행 환경은 따뜻하게 준비되어 있지만 필요할 때 모델은 다시 로드한다. Figure 14의 요청당 시간은 **작업 관리 모델의 평균 시간과 세 도구를 합쳐 실행한 평균 시간을 각각 측정한 다음 더한 추정치**다. 하나의 실제 요청을 처음부터 끝까지 연속 추적해 얻은 분포가 아니다. 따라서 이 그림만으로 p95·p99, 가장 느린 요청, 서비스 부하에 따른 대기열 지연을 알 수 없다. ([원문 §6.3 및 Figure 14](https://arxiv.org/html/2610.13125v1#S6.F14.fig1))

논문은 이 방식으로 네 플랫폼에서 요청 시간 추정치가 9.0–15.9% 감소했다고 보고한다. Arrow에서는 43.78초에서 37.65초로 6.13초가 줄었다. 보고된 두 값으로 직접 나누어 확인하면 6.13÷43.78은 약 14.0%다. 이 계산은 기사에서 수치를 읽기 위한 검산이지 논문이 제시한 새 방정식이나 별도 실험이 아니다. 또 LLM 로딩 구간은 10.40초에서 5.06초로 줄어 51.3% 감소했다고 보고한다. 이 한 구간의 51.3%와 전체 요청 추정치의 14.0%는 분모가 다르다. 논문은 LLM 로딩이 절감의 대부분을 설명한다고 해석한다. ([원문 §6.3, Figure 14 설명](https://arxiv.org/html/2610.13125v1#S6.F14.fig1))

**확인 질문:** 평균을 별도로 구해 더했다면 실제 느린 요청의 상위 1% 지연을 알 수 있을까? **아니다.** 평균값을 더한 추정은 단계 사이 변동, 실제 요청별 상관, 대기열이나 꼬리 지연의 분포를 대신하지 않는다.

## 논문이 말한 구현과 고정 revision에서 읽은 저장소를 분리하기

논문은 `libumsh`가 플랫폼, 데이터 방향, 입출력·커널 경계, 응용의 공유 요구에 맞춰 읽기·쓰기 정책과 구현을 고른다고 설명한다. Arrow와 Lunar에서는 세밀한 일관성 제어를 노출하려고 런타임 수정이 필요했다고 적는다. 그러므로 모든 장치에서 기존 런타임을 그대로 둔 채 바로 쓸 수 있는 만능 API로 소개하면 과장이다. ([원문 §5, §5.1–5.2](https://arxiv.org/html/2610.13125v1#S5))

별도의 공개 artifact 저장소 revision `880d535a86c3d82277f4c546edf386ef16ef7380`에서는 문서와 헤더를 정적으로 읽었다. README는 정책을 데이터 접근과 메모리 bind 속성으로 나눠 기록한다고 설명한다. `policy.hpp`에는 방향(CPU→GPU/GPU→CPU), 경계(IO/커널 내부/커널 사이), Read/Write 정책, 구현 방식, 세분도와 참여 범위, `Unsupported/Experimental/Supported` 상태가 선언되어 있다. Control-plane 안내는 acquire/release를 소유권 원시 기능으로, lock/unlock과 wait/set을 상위 도우미로 구분한다. 안내에 따르면 시스템 범위·스레드 참여만 지원되며, block/grid 참여는 거부되고 공정성은 보장되지 않는다. 성공한 제어 동기화도 payload의 캐시 정책이나 필요한 캐시 처리를 대체하지 않는다.

파일 로더 헤더는 `Direct`, `Copy`, `Mmap` 선택과 파일 경로·범위·캐시 flush 옵션을 선언한다. 이 검토는 해당 헤더의 인터페이스 선언과 README·control-plane 문서만 읽었다. 저장소 전체, 구현 파일, 모든 CSV·plot script, 논문 실행에 사용된 정확한 commit을 대조하지 않았고 빌드나 benchmark를 실행하지 않았다. 그러므로 이 snapshot은 코드 읽기 범위를 넓힌 자료일 뿐, 논문 수치를 재현했거나 동일 실행 버전을 입증하는 증거가 아니다. ([고정 revision 저장소 README](https://github.com/XpuOS/libumsh-artifacts/blob/880d535a86c3d82277f4c546edf386ef16ef7380/README.md), [policy.hpp](https://github.com/XpuOS/libumsh-artifacts/blob/880d535a86c3d82277f4c546edf386ef16ef7380/include/umsh/policy.hpp), [control-plane 문서](https://github.com/XpuOS/libumsh-artifacts/blob/880d535a86c3d82277f4c546edf386ef16ef7380/docs/control-plane.md))

## 결과를 어디까지 일반화할 수 있나

연구는 네 종류의 UMA 플랫폼과 여러 저수준 전달·동기화 경로, 아홉 응용·시스템 사례에서 측정한 결과를 제시한다. 이 근거는 해당 장치·런타임·캐시 정책·작업 경계의 구체적 비교다. 다른 CPU/GPU, 다른 드라이버, 다른 페이지 크기, 다른 요청 구성에서 같은 절감이 나온다고 보장하지 않는다. 저수준 byte 전달, 파일 로딩 구간, 연산자 실행 시간, TTFT, 잠금 오버헤드는 서로 다른 질문이다.

정확성 검사도 모든 공유 프로그램을 증명하지 않으며, 성능 결과도 정확성을 대신하지 않는다. 캐시를 끄거나 운영체제·장치 설정을 임의 변경하라는 절차를 이 글에서 권하지 않는다. 어떤 정책이 맞는지는 해당 플랫폼에서 지원되는 조합, 데이터가 움직이는 방향, 동기화 경계와 실제 workload를 확인해야 한다.

## 다시 읽을 순서

처음이라면 Figure 2에서 물리 메모리 구조를 구분하고 Figure 3에서 데이터 복사와 직접 접근을 나눈 뒤, “같은 주소·최신 값·동시 갱신”을 서로 다른 조건으로 기억하면 된다. 시스템을 구현하는 독자는 §4의 정확성 검사에서 단일 송수신 시험이 보장하는 범위를 읽고, 데이터 경로와 제어 경로의 비교 기준을 따로 확인하면 된다. 성능 수치를 볼 때는 Figure 14가 요청별 실측 분포가 아니라 평균 합산 추정이라는 경계를 먼저 읽는다.
