모델 하나를 호출하는 API와 실제 작업을 수행하는 에이전트 시스템은 다르다. 평가 하네스가 무엇을 고정하고 어떤 변화를 허용하는지 살펴보자.

## 1. 평가 실행 구조

아래는 [Inspect AI의 Task](https://inspect.aisi.org.uk/tasks) 개념을 참고한 설명용 구조다. Dataset, Solver, Scorer가 핵심이고 필요할 때 도구, 샌드박스, 제한 조건을 추가한다.


```text
task manifest + dataset snapshot
              |
              v
       evaluation harness
              |
              v
       agent / solver <---- tool results
              |                   ^
              v                   |
       isolated environment ------+
              |
              v
       independent scorer
              |
              v
       trace + aggregate score
```


| 구성 | 책임 |
|---|---|
| Harness | 환경 초기화, 제한, 시도 관리, 결과 수집 |
| Scaffold | 프롬프트, 기억, 계획, 도구 사용, 반복 |
| Sandbox | 파일·프로세스·네트워크 격리 |
| Verifier | 결과의 성공 여부와 제약 위반 검사 |
| Reporter | 분모, 오류, 시간, 비용, 버전 공개 |

하네스와 스캐폴드의 용어는 평가 프로젝트마다 일부 겹친다. 이름보다 각 기능을 실제로 어느 부분이 책임지는지 확인한다.

## 2. 하나의 과업을 어떻게 시험할까?

가상 코딩 이슈: 빈 입력을 처리하는 파서를 수정하고 기존 API와 정상 입력 동작을 유지하라. 모델은 작업 디렉터리와 문제 설명을 받는다. 실행기에는 터미널 및 파일 편집 도구가 있고, 실제 채점은 별도의 테스트 환경에서 수행한다.

| 단계 | 검증 내용 |
|---|---|
| 준비 | 기준 커밋, 환경 이미지, 문제 ID 고정 |
| 실행 | 코드 읽기·수정·공개 테스트, 시간 제한 |
| 수집 | 최종 패치, 도구 호출, 종료 사유 저장 |
| 검증 | 새 환경에 패치 적용, 숨겨진 테스트 |
| 집계 | 성공·실패·오류와 비용을 기록 |

[SWE-bench](https://arxiv.org/abs/2310.06770)는 실제 저장소의 문제 해결을 코드 변경과 테스트로 평가한다. 과업 완료 판정은 모델의 자신감이나 마지막 메시지가 아니라 채점기에서 나온다.

## 3. 평가 사양을 버전으로 고정하기

다음 YAML은 실제 벤치마크의 공식 설정이 아니라 자체 평가용 예시다. 모델 ID뿐 아니라 실제 응답 모델, 시스템 프롬프트 버전, 도구 권한, 예산을 기록해야 한다.


```yaml
benchmark: toy-repository
dataset_revision: v1
model_snapshot: pinned-model-id
scaffold_revision: scaffold-v1
environment_image: example-image-digest
grader_revision: grader-v1
tools:
  - read_workspace
  - edit_workspace
  - run_public_tests
network: disabled
timeout_seconds: 600
max_tool_calls: 50
attempts_per_task: 3
seed_policy: recorded_if_supported
infrastructure_retry: at_most_once
score: hidden_tests_all_pass
```


실제 환경 이미지에는 태그가 아닌 digest를 기록하는 것이 좋다. API 모델의 내부 업데이트가 고정되지 않는 경우 실행 시각과 응답에 표시된 모델 ID를 남긴다. 난수 시드를 지원하더라도 모든 외부 서비스가 결정적이라는 뜻은 아니다.

## 4. 모델 효과와 시스템 효과를 분리하기

두 모델과 두 하네스를 모두 평가하는 가상 2×2 비교를 설계한다.

| 가상 점수 | H1 공통 환경 | H2 도구 확장 환경 |
|---|---:|---:|
| 모델 A | 40% | 65% |
| 모델 B | 50% | 60% |

H1에서 A는 B보다 10%p 낮지만 H2에서는 5%p 높다. A의 하네스 개선은 25%p, B는 10%p이다. 단순 차이의 차이(Difference-in-differences)는 15%p로, 이 설계에서 모델과 하네스의 상호작용을 요약한다. 통계적 결론에는 반복 및 짝지어진 과업 분석이 필요하다.

실제 [Inkling 2 Mini 모델 카드](https://thinkingmachines.ai/model-card/inkling-2-mini/)에서도 Chartography의 Python 허용 조건과 기본 조건이 다르다. 비교 실험에서는 모델 외 변수를 하나씩 변경한다. 동일 예산에서의 비교와 각 모델의 최적 설정 비교를 별도 표로 제시한다.

## 5. 실행기와 채점기를 분리하는 이유

평가 에이전트는 허용된 작업만 수행한다. 채점기의 정답, 숨겨진 테스트, 결과 레코드 및 검증기 실행 권한은 에이전트에게 제공하지 않는다. 각 시도는 초기 상태를 복원하고, 검증에 필요한 산출물만 전달한다.

실패 유형도 구분한다. 과업 미완료, 시간 초과, 정책 위반, 환경 초기화 오류, 채점기 오류는 서로 다르다. 전체 분모에서 제외할 조건을 미리 지정하고 전체 수와 제외 사유를 공개한다. 평가 중 발생한 문제로 임의로 성공 기준을 완화하지 않는다.

실습으로 [Inspect AI](https://inspect.aisi.org.uk/)나 [LM Evaluation Harness](https://github.com/EleutherAI/lm-evaluation-harness)를 살펴보며 한 과업의 데이터셋, solver, scorer를 찾아보자. 다음 편에서는 이 구성의 어느 부분이 오염되거나 악용될 수 있는지 다룬다.
