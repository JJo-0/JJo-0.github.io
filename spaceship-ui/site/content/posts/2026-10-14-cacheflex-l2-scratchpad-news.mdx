> **연구 작업본 · MICRO 2026 게재 예정.** arXiv v1은 2026년 10월 9일 제출됐고 10월 12일 신규 목록에 공지됐다. 아래 수치는 실제 상용 CPU 실리콘의 측정값이 아니라 단일 코어 gem5 시뮬레이션과 상용 12nm 공정의 post-layout 평가를 결합한 저자 보고다.

## 1. 한 문장 결론

**CacheFlex는 private L2 캐시의 일부 way를 실행 중 software-managed scratchpad memory(SPM)로 전환해, 넓은 SIMD 벡터가 L1 용량 한계 때문에 반복하는 데이터 이동을 줄인다.** 논문의 대표 조건에서 커널 기하평균 성능은 512-bit에서 1.12배, 2048-bit에서 1.44배로 커졌지만, 모든 CPU 작업이 같은 이득을 얻는다는 뜻은 아니다.

## 2. 왜 어려운가

CPU의 벡터 폭을 넓혀도 L1 data cache의 크기는 그대로다. 재사용할 tile이 L1에 머물지 못하면 L1과 L2 사이 traffic이 늘고 실행 유닛은 데이터를 기다린다.

L1은 core pipeline과 강하게 결합되어 단순히 키우기 어렵다. 반면 더 큰 private L2는 하드웨어가 replacement와 coherence를 관리하므로 일반 프로그램이 데이터를 고정하거나 직접 읽을 수 없다.

## 3. 기초 개념

Cache는 하드웨어가 자동 관리하지만 scratchpad는 프로그램이 데이터의 배치와 수명을 정한다. GEMM처럼 reuse pattern을 아는 작업에서 불필요한 교체를 피할 수 있다.

CacheFlex의 핵심은 SRAM을 새로 붙이는 것이 아니다. 기존 512KB private L2의 일부 way를 SPM으로 바꾸고, 나머지는 일반 cache로 유지한다. `spm_cp`는 coherent memory에서 SPM으로, `spm_wb`는 반대 방향으로 데이터를 옮긴다. `spm_ld`와 `spm_st`는 L1 pipeline을 거치지 않고 SPM을 직접 사용한다.

## 4. 기존 방식의 한계

Hardware prefetch와 L2 hint는 데이터를 미리 가져오지만 residency를 보장하거나 L1 pipeline을 우회하지 못한다. 별도 scratchpad SRAM은 명시적 제어가 가능하지만 면적을 고정적으로 지불한다.

이상화한 L2 pinning+non-temporal load도 L1 pipeline은 우회하지 못한다. CacheFlex는 W3·W5에서 이 비교군보다 1.63배·1.34배 빨랐지만, 모델링된 단일 코어 결과다.

## 5. 새 방법의 세 단계

운영체제나 runtime이 thread-private SPM을 할당한다. 프로그램은 반복 사용할 tile을 `spm_cp`로 stage하고 `spm_ld`로 읽은 뒤, `spm_wb`로 결과를 돌려보내거나 해당 way를 cache로 반환한다.

일반 memory와 SPM은 ordering 규칙이 다르다. 연구진은 bridge 명령을 일반 LSQ와 SPM LSQ 양쪽에 넣어 hazard를 조정한다. Context switch 때는 진행 중 접근을 drain하고 owner-thread ID로 다른 thread의 resident SPM 접근을 막는다.

## 6. 시스템 경계와 물리량

이 논문의 중심은 하나의 닫힌 수식보다 **working-set 크기, cache 용량, vector length, 데이터 이동량**의 관계다. 모델은 2.5GHz Armv8-A out-of-order core, 64KB L1D, 512KB L2와 4MB L3를 사용했고 vector length는 512·1024·2048-bit로 바꿨다.

핵심 경계조건은 재사용할 데이터가 SPM에 맞고 접근 패턴을 software가 미리 안다는 것이다. 작업집합이 너무 작으면 기존 cache가 이미 잘 동작하고, 너무 크면 SPM도 병목을 없애지 못한다. 실제로 unfused attention의 4096-token score matrix는 32MB여서 L2와 SPM을 모두 훨씬 넘었고, attention 자체의 속도 향상은 거의 없었다.

## 7. 실험과 수치

일곱 GEMM shape를 양쪽 설계에 맞게 각각 tuning했다. 512-bit에서는 기하평균 1.12배 성능과 memory-subsystem energy 26% 감소를, 2048-bit에서는 1.44배와 40% 감소를 보고했다.

Full layer에서는 LLaMA-3.2-1B와 BERT-Base의 prefill을 평가했다. FlashAttention과 결합한 BERT-Base, sequence length 4096, vector length 2048-bit에서 최대 1.78배 성능과 45% memory-subsystem energy 절감을 보고했다. LLaMA 조건의 대표 최대치는 1.64배와 38%였다. 이 에너지는 전체 시스템 전력이 아니라 cache·SPM·DRAM을 합친 memory subsystem 범위다.

12nm post-place-and-route에서 추가 SPM LSQ와 control logic은 8,377µm²였다. L2 자체 증가는 0.31%, SPM LSQ까지 L2 면적 기준 총 overhead는 2.02%다.

## 8. 반대 증거

이득이 항상 크지는 않았다. 512-bit W6는 reused panel이 작아 1.05배에 그쳤다. FlashAttention에서도 per-head K+V가 L2의 절반 이하인 sequence length 1024 이하에서는 0~3.2%였다.

또한 성능은 gem5, 에너지는 RTL access energy와 simulated access count의 결합이다. 완성된 CPU 실리콘, multicore contention, 실제 OS scheduler, 다양한 application을 통합해 측정하지 않았다. 2048-bit SVE 구현도 현재 상용 CPU 전체를 대표하지 않는다.

## 9. 한계

평가는 single-core mechanism-level 범위다. Thread 간 SPM scheduling, shared contention, 보안·side-channel, 잦은 preemption의 spill/fill 비용은 검증되지 않았다. Graph analytics와 sparse linear algebra 확장은 전망일 뿐 측정 결과가 아니다.

공개 artifact에는 gem5 model, benchmark, measurement와 재현 스크립트가 있지만 이번 작업에서는 직접 실행하지 않았다.

## 10. 실제 변화

설계 포인트는 “더 큰 cache”가 아니라 **자동관리 영역과 명시적 관리 영역을 실행 중 나누는 계약**이다. 더 넓은 vector를 쓸수록 residency와 movement를 ISA·OS·microarchitecture가 함께 다루는 일이 중요해진다.

## 11. 다음 재검토 트리거

MICRO 최종판 공개, artifact 독립 재현, FPGA·실리콘 프로토타입, multicore와 실제 OS 통합, irregular workload 결과가 나오면 결론을 갱신해야 한다. 특히 전체 chip area·power 기준 overhead와 context-switch가 잦은 환경의 tail latency가 필요하다.
